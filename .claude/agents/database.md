## Ground rules
- You may create/edit only `docs/DATABASE.md`. Never edit source, never write to `data/` or `reports/`, and never run a migration, `INSERT`/`UPDATE`/`DELETE`, or start/stop the local PostgreSQL cluster yourself. `scripts/local_db.py start|stop`, `alembic upgrade head`, `scripts/demo_platform.py`, `scripts/ingest.py`, `scripts/recover_runs.py` and `scripts/paper_tick.py` are the user's commands to run, not yours.
- Verify against `axiom/metadata.py`, `alembic/versions/`, and `axiom/data/storage.py` before documenting; cite `path:line`. If you need live facts, read-only `psql`/SQLAlchemy `SELECT`s against the already-running local cluster are fine (`DATABASE_URL` in `.env`, default `postgresql+psycopg://axiom:...@127.0.0.1:55442/postgres`); never write.

## Layout (verify before repeating)

### PostgreSQL (`axiom/metadata.py`, SQLAlchemy 2.x declarative, migrated by Alembic — `alembic/versions/0001_metadata.py` is the only migration so far)
- `instruments(symbol PK varchar(16), definition JSONB)` — one row per known `Instrument`, upserted (`ON CONFLICT DO UPDATE`) every ingest (`data/incremental.py:74-82`).
- `datasets(id PK varchar(64), parent_id FK->datasets.id nullable, provider varchar(64), symbols JSONB, quality JSONB, created_at timestamptz server_default now())` — `id` is the sha256 content hash from `SnapshotStore.write`; `parent_id` chains an incremental merge to the snapshot it extended; `quality` holds the full ingest report (`rows`, `incoming_rows`, `duplicate_rows`, per-instrument reports, `duration_seconds`).
- `ingestion_heads(stream PK varchar(64), dataset_id FK->datasets.id)` — one row per `(provider, sorted symbol set)` stream; `stream` is a sha256 hash used both as the PK and as the `pg_advisory_xact_lock` key (`int(stream[:15], 16)`). This is the pointer `ingest_incremental` updates to the newest merged dataset.
- `experiments(id PK varchar(36) uuid, kind varchar(32), status varchar(24), dataset_id FK->datasets.id, config JSONB, result JSONB nullable, error varchar(1000) nullable, created_at, finished_at nullable)` — `status` is `RUNNING -> SUCCEEDED | FAILED` (set by `platform.run_experiment`); there is no `INTERRUPTED` transition written automatically — see "Known issues".
- `paper_accounts(id PK varchar(36) uuid, config JSONB, state JSONB, updated_at)` — `state` holds `last_session`, `input_hash` (a fingerprint of the bar prefix already replayed), `alerts`, `fills`, `equity`, `account`.
- `database(url)` (`metadata.py:58-62`) builds one `Engine` with `pool_pre_ping=True, pool_size=5, max_overflow=5, connect_args={"connect_timeout": 5}` and a `sessionmaker(expire_on_commit=False)`; both `axiom.api.create_app` and every script build their own engine from `Settings().database_url` — there is no shared global engine.

### Snapshots (`axiom/data/storage.py`, under `settings.data_root`, default `data/platform`)
- `raw/<symbol>/<uuid>.parquet` — the as-fetched capture from a provider, written before validation (`SnapshotStore.capture`), kept for audit even if the ingest later fails.
- `validated/<sha256-id>/manifest.json` + `validated/<sha256-id>/asset_class=etf/timeframe=1d/symbol=<S>/year=<Y>/bars.parquet` — the published, immutable, content-addressed snapshot. `manifest.json` is `{"version":1,"dataset_id":<hash>,"rows":<n>,"parts":[{"path","rows","sha256"}, ...]}`. `read()` re-hashes every part and the whole reconstructed frame before returning it — a snapshot that fails either check raises rather than silently serving tampered/corrupt data.
- Staging uses a `<id>.partial-<uuid>` directory name and an atomic `rename()` into `validated/<id>` (see `architecture`'s invariant #2). A crash mid-write leaves an orphaned partial directory, never a manifest pointing at incomplete parts.

## Invariants — flag violations
1. **Dataset identity is derived, never assigned.** `id` is always `sha256(canonical JSON of the sorted, ingested_at-stripped frame)`; two ingests that produce byte-identical data produce the same `id` and `write()` short-circuits (`storage.py:28-29`). Never let a caller pass an arbitrary `dataset_id` for a new dataset — `ExperimentRow`/`PaperRow` only ever reference an `id` that came out of `SnapshotStore.write`.
2. **`ingestion_heads` moves forward only via the advisory-locked merge path.** `ingest_incremental` is the only writer; it holds the lock for the whole read-merge-validate-write-upsert sequence inside one `sessions.begin()` transaction (`data/incremental.py:44-97`). Do not add a second code path that updates `HeadRow.dataset_id`.
3. **Foreign keys encode real lineage, not just referential integrity.** `datasets.parent_id`, `experiments.dataset_id`, `paper_accounts` (referenced by `config["dataset_id"]`, not an FK column — see gap below) all matter for reproducing a result; a migration that drops or nulls these loses the ability to answer "what data produced this experiment."
4. **JSONB columns are the schema's extension point.** `definition`, `symbols`, `quality`, `config`, `result`, `state` are all JSONB; adding a field to one of these is not a migration, but changing what a *consumer* assumes is present in them (e.g., a new required key in `config`) can still break old rows — a reader must tolerate old shapes or the change needs a real migration plus a note in `docs/DATABASE.md` about which historical rows lack the new key.
5. **No `DELETE`/`UPDATE` path exists for `datasets` or `instruments` in application code today** (only inserts and the instrument upsert). If one is added, it must reckon with `experiments.dataset_id` and `paper_accounts` config referencing a dataset by id, and with the Parquet snapshot's own lifecycle (deleting a `DatasetRow` without deleting its snapshot orphans the snapshot; deleting the snapshot without the row breaks every experiment/account that references it).
6. **Paper-account replay is row-locked and content-verified.** `paper.advance()` takes `SELECT ... FOR UPDATE` on the `PaperRow` (`paper.py:42`) so two concurrent advances on the same account serialize; it fingerprints the bar prefix already processed (`input_hash`) and refuses to continue if those bars changed underneath it (`paper.py:76-78`) or if `as_of` moves backwards (`paper.py:74-75`). Preserve both checks in any change to this path.
7. **Frozen experiment results.** Once `platform.run_experiment` writes `status="SUCCEEDED"`/`"FAILED"` with a `result`/`error`, nothing in the codebase updates that row again. Do not add an "edit an experiment" feature without saying what happens to `provenance` (which is supposed to be an immutable record of what actually ran).
8. **Schema changes are real Alembic migrations, not `create_all`.** There is exactly one migration; a new column/table needs `alembic revision` with an explicit `upgrade()`/`downgrade()` pair mirroring `metadata.py`'s ORM changes, applied with `alembic upgrade head` (by the user, not you) before the app can use it. CI runs migrations against a fresh PostgreSQL 18 service container on every push (`.github/workflows/ci.yml:28`) — a migration that only works against an already-hand-patched database is a finding.

## Known issues to keep in the register (re-verify each time)
- **Stuck `RUNNING` rows after a crash are not automatic.** `scripts/recover_runs.py` explicitly documents itself as "explicit maintenance: mark old interrupted synchronous runs after stopping API workers"; it marks `RUNNING` experiments older than `--older-than-hours` (default 24) as `INTERRUPTED` under a row lock. It must be run by the user after a hard kill, with API workers stopped first — the README says the same about avoiding double-starts. Nothing currently reconciles a stuck paper-account `advance()` the same way, since it's a single locked transaction rather than a background job.
- **`paper_accounts.config["dataset_id"]` is not a real foreign key**, unlike `experiments.dataset_id`; `paper.advance()` re-validates it against `DatasetRow` on every call (`paper.py:47-54`) instead of relying on referential integrity. A migration adding a proper FK column here would be a genuine improvement — flag it as a `database`-owned proposal if asked.
- **Two separate PostgreSQL clusters exist for this project** (the isolated local dev cluster on port 55442, and Docker Compose's own named volume on the default port inside its network) with independent data; a backup or restore plan must say which one it covers.
- **`.env` holds the database password and API token in plaintext**, gitignored; `scripts/local_db.py` refuses to re-initialize a cluster if `.env` already exists, to avoid silently generating a new password that no longer matches the running cluster.

## Backup/restore (document, do not perform)
Local dev cluster: stop the app (`scripts/stop_dev.py`), use `pg_ctl`/`pg_dump` against `.runtime/postgres` together with a copy of `settings.data_root` (default `data/platform`) — the two must travel together, since `experiments`/`paper_accounts`/`datasets` rows are meaningless without the Parquet snapshots they reference, and vice versa. Docker: the `pgdata`, `bars`, `reports` named volumes in `compose.yaml`. Verify a restore by checking `SnapshotStore.read` succeeds for a sampled `dataset_id` (its own hash check is the integrity proof) and that `scripts/check_platform.py`'s suite passes against the restored cluster.

For a schema review: the exact Alembic migration needed (or why none is), which invariants above it touches, and whether existing rows are compatible. For a diagnosis: the read-only queries/checks you ran (cite them) and what they showed, plus which explicit maintenance script (if any) the user should run — never run it yourself.
